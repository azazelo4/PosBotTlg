# Деплой на VPS (is*hosting, Казахстан)

Бот и MySQL работают в Docker Compose на Ubuntu-VPS, деплой — GitHub Actions через self-hosted
runner на этом же сервере. Общая часть — в [`DEPLOY.md`](DEPLOY.md).

Выбранный сервер: **is*hosting VPS Kazakhstan, тариф Start** — 2 vCPU, 2 GB RAM, 30 GB SSD.
Сервер в Казахстане выбран и из-за требования закона РК о персональных данных хранить такие базы
на территории РК (в БД — имена и телефоны сотрудников).

```
GitHub (push в POS-Bot)
   │  job check + test — на раннерах GitHub
   │  job deploy ──────────────┐
   ▼                           │ runner сам забирает задачу исходящим HTTPS
VPS (Ubuntu 24.04)             │
   ├─ GitHub runner  ◄─────────┘
   └─ docker compose: bot ──► api.telegram.org (long polling)
                      web (админка + API кассы) ◄── caddy :443 (HTTPS) ◄── браузер / Telegram Mini App
                      db (MySQL, volume pos-bot_db_data)
                      adminer (только 127.0.0.1:8080)
```

Бот сам опрашивает Telegram, runner сам ходит в GitHub. Входящие порты: SSH, а для веб-админки и
кассы-приложения — 80/443.

---

## 1. Заказ сервера

В панели is*hosting: **VPS → Kazakhstan → Start**.

| Параметр | Значение |
|---|---|
| ОС | Ubuntu 24.04 |
| Панель управления | не нужна |
| SSH-ключ | добавить свой публичный ключ, если панель позволяет (иначе — шаг 2) |
| Оплата | помесячно; при оплате за год обычно дешевле |

После активации в панели будут IP-адрес и пароль root.

## 2. Первый вход и SSH-ключ

С ноутбука (если ключа ещё нет — `ssh-keygen -t ed25519`):

```bash
ssh-copy-id root@<IP>     # ввести пароль root из панели
ssh root@<IP>             # теперь без пароля
```

Ключ нужен до следующего шага: скрипт подготовки отключит вход по паролю, только если увидит ключ.

## 3. Подготовка сервера

С ноутбука, из каталога репозитория:

```bash
scp deploy/setup-server.sh root@<IP>:~
ssh root@<IP> 'bash setup-server.sh'
```

[`deploy/setup-server.sh`](../deploy/setup-server.sh) (повторный запуск безопасен):

- часовой пояс `Asia/Almaty`, обновление системы и автообновления безопасности;
- swap 2 GB — запас для сборки образа и пиков MySQL;
- Docker и ротация логов контейнеров;
- пользователь `gh-runner` для GitHub runner, каталог `/opt/pos-bot`;
- ежедневный бэкап БД в 03:30;
- firewall `ufw`: входящие SSH, 80 и 443 (для веб-админки); `fail2ban`;
- вход по SSH только по ключу.

Проверка:

```bash
ssh root@<IP>
docker run --rm hello-world
free -h          # Swap: 2.0Gi
ufw status       # OpenSSH, 80/tcp, 443/tcp — ALLOW
```

> Если провайдер поддерживает cloud-init при создании сервера, вместо шагов 2–3 можно вставить
> [`deploy/cloud-init.yaml`](../deploy/cloud-init.yaml) — он делает то же, кроме swap, ufw и fail2ban.

## 4. GitHub: runner

Секреты и переменные в GitHub **не нужны** — всё задаётся в мастере `/setup` после деплоя
(см. [`DEPLOY.md`, раздел 1](DEPLOY.md#1-настройки-github--не-нужны)). Достаточно создать environment
`production` и в **Deployment branches** ограничить его веткой `POS-Bot`.

Если токен бота ещё не перевыпущен после утечки в истории git — сделать это сейчас: @BotFather → `/revoke`,
новый токен ввести в мастере `/setup`, а если бот уже настроен — на сервере (после `/revoke` бот не работает,
и войти в «Настройки» по ссылке из бота нельзя):

```bash
cd /opt/pos-bot
read -rsp 'Новый токен: ' T; echo; printf '%s\n' "$T" | docker compose exec -T web python -m setup_code --token; unset T
```

Если токен задан строкой `TOKEN=` в `.env` или секретом `TOKEN` в GitHub, команда скажет об этом — тогда
замените его там (секрет — **Settings → Secrets and variables → Actions**) и перезапустите: `docker compose up -d`.

**Runner.** GitHub: **Settings → Actions → Runners → New self-hosted runner → Linux → x64**. Страница
покажет команды с актуальной версией и одноразовым токеном (действует час). Выполнить на сервере:

```bash
sudo -iu gh-runner
cd ~/actions-runner
# curl ... и tar ... — скопировать со страницы GitHub
./config.sh --url https://github.com/azazelo4/PosBotTlg --token <ТОКЕН_СО_СТРАНИЦЫ> \
            --name ishosting-pos-bot --labels pos-bot --unattended
exit

cd /home/gh-runner/actions-runner
./svc.sh install gh-runner      # от root: runner как сервис, переживает перезагрузку
./svc.sh start
```

В GitHub runner должен появиться со статусом **Idle** и метками `self-hosted, Linux, X64, pos-bot`.

## 5. Первый деплой

1. **Actions → Check & Deploy → Run workflow** (ветка `POS-Bot`) или любой push в `POS-Bot`.
   Если деплой уже стоял в очереди «Waiting for a runner», он запустится сам.
2. Job `deploy` разложит код в `/opt/pos-bot`, создаст `.env` (пароли БД и ключ шифрования — один раз)
   и поднимет контейнеры. На чистом сервере деплой зелёный, бот ждёт настройки.
3. **Домен** (нужен для HTTPS, кассы-приложения и удобного входа): в DNS запись **A → IP сервера**.
   Без своего домена подойдёт бесплатный `<IP-через-дефисы>.sslip.io`, например `203-0-113-10.sslip.io`
   для IP `203.0.113.10`. Сертификат Caddy выпустит сам при первом заходе.
4. **Код настройки** на сервере:

   ```bash
   cd /opt/pos-bot
   docker compose ps                              # bot, web, caddy, db (healthy) — Up
   docker compose exec web python -m setup_code   # Код настройки: XXXX-XXXX-XXXX
   ```

5. Открыть `https://<домен>/setup`, ввести код, токен от @BotFather, ИП, магазины, свой телефон,
   адрес веб-админки (подставится сам). Без домена — через SSH-туннель:
   `ssh -L 8000:127.0.0.1:8000 root@<IP>` и <http://127.0.0.1:8000/setup>.
6. Через 10–20 секунд: `docker compose logs --tail=20 bot` → «Бот запущен, начинаю опрос Telegram.»
7. В Telegram с указанного номера: `/start` → «Поделиться номером» → меню администратора.
8. Добавить сотрудников: **Персонал → Добавить пользователя** (в боте или в веб-админке).

## 6. Веб-админка и касса-приложение

Если при настройке указан адрес веб-админки (`https://<домен>`), всё уже работает: Caddy выпускает
сертификат только для этого домена, порты 80 и 443 открыты скриптом подготовки.

1. Проверка: `https://<домен>/health` → `{"ok":true,"configured":true}`.
2. В боте: заново `/start` — у пользователей появится кнопка **«📷 Касса»** рядом с полем ввода,
   у менеджеров и администраторов — кнопка **«Веб-админка»** в меню.
3. Сменить домен позже: веб-админка → **Настройки** → «Адрес веб-админки».

В @BotFather ничего настраивать не нужно: касса открывается кнопкой бота, ей не требуется привязка домена.

**Ценники.** По умолчанию 30×20 мм — рулон «2×3» для **Xprinter XP-365B** (203 dpi). Для другого размера —
веб-админка → **Настройки** → «Ширина/высота ценника» (ширина — поперёк ленты); размер можно задать
и при печати. Узкие высокие этикетки (например, 20×30) печатаются в вертикальной раскладке автоматически.

Настройка XP-365B на компьютере с Windows (один раз):

1. Установить драйвер Xprinter с сайта производителя (если принтер уже печатает ценники Paloma — драйвер стоит).
2. **Панель управления → Устройства и принтеры → XP-365B → Настройка печати → Бумага/Page Setup → New**:
   ширина 30 мм, высота 20 мм, тип носителя — этикетки с зазором (Gap/Labels with gaps). Выбрать этот размер по умолчанию.
3. Если принтер «съезжает» на соседнюю этикетку — откалибровать датчик зазора: с заправленным рулоном зажать
   кнопку **FEED**, пока принтер не протянет несколько этикеток (точная последовательность — в инструкции к модели).
4. Печать PDF из браузера или Adobe Reader: принтер XP-365B, размер бумаги 30×20, масштаб **100 % / «Фактический
   размер»**, поля — нет. Первую печать сделать на 1–2 этикетках и проверить, что QR сканируется кассой.

## 7. Бэкапы

Ежедневно в 03:30 [`deploy/backup.sh`](../deploy/backup.sh) делает `mysqldump` в `/opt/pos-bot-backups`
и хранит 14 дней. Проверить вручную:

```bash
/opt/pos-bot/deploy/backup.sh
ls -lh /opt/pos-bot-backups
```

**Копия вне сервера.** Бэкап на том же диске пропадёт вместе с сервером, поэтому стоит регулярно
забирать копии к себе:

```bash
# с ноутбука или другого сервера, например раз в неделю по cron
rsync -av root@<IP>:/opt/pos-bot-backups/ ~/pos-bot-backups/
```

Либо автоматически в S3-совместимое хранилище: в `/etc/pos-bot-backup.env` задать `BACKUP_PAR_URL` —
URL, по которому разрешена PUT-загрузка (имя файла дописывается в конец).

**Восстановление:**

```bash
cd /opt/pos-bot
docker compose stop bot
gunzip -c /opt/pos-bot-backups/bot_YYYYMMDD_HHMM.sql.gz | \
  docker compose exec -T -e MYSQL_PWD="$(grep -m1 '^MYSQL_ROOT_PASSWORD=' .env | cut -d= -f2-)" db mysql -uroot bot
docker compose start bot
```

> **Сохраните и `/opt/pos-bot/.env`** (в менеджер паролей или зашифрованным архивом, не в git):
> в нём пароли БД и `POSBOT_MASTER_KEY`, которым зашифрованы токен бота и ключи Webkassa в базе.
> Без ключа дамп восстановится, но токен и ключи придётся ввести в «Настройках» заново.

## 8. Перенос данных со старого сервера

Когда старый сервер снова будет доступен:

```bash
# на старом сервере
cd /opt/pos-bot
docker compose stop bot          # важно: два бота с одним токеном конфликтуют (ошибка 409)
docker compose exec -T -e MYSQL_PWD=<root-пароль> db \
  mysqldump -uroot --single-transaction --routines --triggers --no-tablespaces bot | gzip > old_bot.sql.gz
scp old_bot.sql.gz root@<IP>:/tmp/
```

На новом сервере — шаги «Восстановление» с файлом `/tmp/old_bot.sql.gz`. При старте бот сам добавит
недостающие таблицы и колонки. Затем на старом сервере `docker compose down` и отключить автозапуск,
чтобы он не поднялся с тем же токеном.

## 9. Обслуживание

| Задача | Команда (на сервере, в `/opt/pos-bot`) |
|---|---|
| Логи бота | `docker compose logs -f --tail=100 bot` |
| Перезапуск | `docker compose restart bot` |
| Adminer | с ноутбука: `ssh -L 8080:127.0.0.1:8080 root@<IP>`, затем <http://localhost:8080> (сервер `db`) |
| Память и диск | `free -h`, `df -h /`, `docker system df` |
| Статус runner | `/home/gh-runner/actions-runner/svc.sh status` |
| Очистка старых образов | `docker image prune -f` (деплой делает это сам) |

Обновления безопасности ставятся автоматически. Раз в пару месяцев: `apt full-upgrade && reboot` —
контейнеры (`restart: always`) и runner (сервис) поднимутся сами.

## 10. Если что-то не так

| Симптом | Причина и решение |
|---|---|
| Job `deploy` висит «Waiting for a runner» | Runner offline или без метки `pos-bot`: `svc.sh status`, метки в Settings → Actions → Runners. |
| Jobs `check`/`test` висят в очереди | Раннеры GitHub для приватного репо расходуют бесплатные минуты (2000 в месяц на Free). Проверить Settings → Billing. |
| Бот пишет «ожидает настройки» | Мастер `/setup` ещё не пройден: `docker compose exec web python -m setup_code`, затем `https://<домен>/setup`. |
| Деплой: «нет MYSQL_PASSWORD, но том базы уже существует» | `.env` на сервере потерян, а база осталась. Восстановить `.env` из копии (или задать секреты `MYSQL_*`) — новый пароль к старой базе не подойдёт. |
| После переноса секреты «не расшифровываются» | Сменился `POSBOT_MASTER_KEY` в `.env`. Вернуть старый ключ или заново ввести токен и ключи Webkassa в «Настройках». |
| В логах `409 Conflict: terminated by other getUpdates request` | Тот же токен опрашивает другой экземпляр бота (старый сервер, локальный запуск). Остановить лишний. |
| Сборка образа падает или сервер «задыхается» | Мало памяти: `free -h`, проверить, что swap включён (`swapon --show`). |
| Касса или админка не открываются, в логах Caddy ошибка сертификата | DNS ещё не обновился или A-запись указывает не туда: `nslookup <домен>`. Порты 80/443 должны быть открыты. |
| «Откройте кассу из Telegram-бота» | Mini App открыли в обычном браузере. Она работает только из Telegram — кнопка «📷 Касса». |
| Нет доступа по SSH после настройки | Войти через консоль (VNC) в панели is*hosting, проверить `/etc/ssh/sshd_config.d/10-pos-bot.conf` и ключ в `~/.ssh/authorized_keys`. |
